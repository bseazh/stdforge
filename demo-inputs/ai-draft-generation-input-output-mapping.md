# AI 标准草案生成：输入、输出与缺口映射

## 结论

这五份参考 PDF 能反推出最终标准必须具备的要素，但**不能可靠地逐字还原原始研发 DOC**。最终标准通常经过立项、试验、评审和规范化编写，原始文档往往只包含产品设计目标、验证记录和问题清单。

因此，StdForge 的正确做法不是“从 PDF 猜原 DOC”，而是以反推字段做输入校验：研发文档缺什么，系统就明确提示什么，并把未知内容留为“待确认”。

## 研发输入到三类输出的映射

| 研发输入字段 | 标准草案 | 编制说明 | 预研报告 |
| --- | --- | --- | --- |
| 项目背景、目标市场、用户场景 | 范围 | 编制目的和意义 | 立项必要性、用户与应用场景 |
| 产品型号、配置、适用范围和排除项 | 范围、分类与型号 | 编制工作简况 | 技术路线 |
| 术语、部件定义 | 术语和定义 | 主要技术内容说明 | 技术路线 |
| 功能、性能、安全、可靠性指标 | 技术要求 | 主要技术内容说明 | 关键指标与风险 |
| 样品、环境、仪器、方法、公式 | 试验方法 | 主要技术内容说明 | 验证方案 |
| 抽样、复测、判定、交付规则 | 检验规则、附录 | 实施建议 | 后续计划 |
| 标准/法规/企业规范清单 | 规范性引用文件 | 编制依据、与现行标准关系 | 合规关注点 |
| 争议、未知数据、待确认问题 | 条款中的待确认标记 | 其他说明 | 风险与后续计划 |

## 最小可跑通输入

为实现“30 秒内生成三类可编辑文档”的黑客松演示，上传材料至少应提供：

1. 产品名称、型号、应用场景与适用范围。
2. 至少 5 条可量化指标，每条包含对象、条件、限值、单位和判定方式。
3. 每类指标至少一套试验条件/步骤；不知道的字段可以写“待确认”。
4. 至少 1 份已知参考文件或法规线索。
5. 样品数量、数据采集方式和验收/复测规则。

## 系统处理合同

```text
DOCX / PDF / TXT
  -> MinerU 或本地文本提取
  -> 字段识别与缺口检查
  -> 选择 JSON 行业模板
  -> LLM 生成 Markdown 中间稿（条款附来源字段）
  -> 人工编辑与版本留痕
  -> 导出标准草案、编制说明、预研报告（DOCX / PDF）
```

## 必须提示人工确认的字段

- 标准编号、归口单位、起草单位、发布日期和替代关系。
- 规范性引用文件的现行有效性和适用范围。
- 性能数值、统计规则、抽样方案和合格判定。
- 产品安全、环保、材料接触和目标市场法规。
- 试验设备精度、测点布置、负载量、振动谱等可重复性条件。
