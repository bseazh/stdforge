# 标准智编实施蓝图

> 本文是项目的实施基线：解释每个模块要解决什么问题、输入输出是什么、当前已经做到哪里，以及后续应按什么顺序落地。产品范围以 [PRD](PRD.md) 为准；本文不将黑客松演示能力误写为生产能力。

## 1. 实施目标

标准智编的目标不是“让 AI 自动写完一份标准”，而是把标准文本及其制修订过程转化为可追溯、可审核、可协作的数据流程：

```text
公开元数据 / 合法上传文件
        -> 原件存证与解析
        -> 标准条款树
        -> 规则审核 + AI 候选建议
        -> 人工修订、评论、评审
        -> 版本快照、导出与通知
        -> 关联公告、组织与政策依据
```

实施时始终遵循四条原则：

1. **原件不改**：PDF / DOCX 原件、来源 URL、文件哈希和解析版本必须保留。
2. **结构化优先**：编辑和审核围绕条款对象，不围绕“直接改 PDF”。
3. **AI 不越权**：AI 只能产生候选内容、提取结果或解读草稿；发布与结论必须人工确认。
4. **授权与可追溯**：只处理已获授权或公开可访问的内容；每一条外部信息都记录来源和时间。

## 2. 当前阶段与实现边界

| 层级 | 本阶段目标 | 已有实现 | 暂不承诺 |
| --- | --- | --- | --- |
| 黑客松 MVP | 跑通一条可信演示主链路 | 工作台、标准条款展示、审核/修订状态、PDF 解析入口、邮件/飞书接入位、线上站点 | 多人并发、真实采集、正式发布系统对接 |
| 可试用版本 | 从演示数据过渡到受控真实数据 | API 契约、MinerU 解析服务、部署与密钥注入方式 | 全量标准库、无人工审核的自动发布 |
| 生产版本 | 可审计的标准协同平台 | 作为后续架构目标 | 绕过版权、登录、反爬或下载限制 |

### 当前已完成的基础能力

- 静态标准协同工作台已上线，可完整演示标准概览、条款、审核问题、修订与政策关联。
- PDF 解析服务可在配置 `MINERU_TOKEN` 后运行，支持上传、解析、Markdown / ZIP 结果查看和下载。
- 发起评审通过服务端 SMTP 向预配置评审组发送通知，浏览器不接触收件人和授权码。
- 解析后的 Markdown 可在配置飞书应用凭据后追加到有编辑权限的飞书文档。
- `main` 推送通过 GitHub Actions 自动同步至服务器并更新站点。

### 当前明确仍为演示的数据与能力

- 标准公告、组织关系、企业关联、政策条目和部分审核结论。
- 条款保存、评论、版本快照的持久化数据库。
- 真实多人在线协同、权限体系、正式 DOCX/PDF 出版。
- 对国家标准网站或第三方来源的自动化采集任务。

## 3. 总体技术分层

```text
展示层
  ├─ 标准协同工作台（index.html / app.js）
  ├─ PDF 解析工作区（pdf-parser/）
  └─ 邮件测试页 / 后续管理后台

服务层
  ├─ 标准导入与解析 API
  ├─ 规则审核与 AI 编排 API
  ├─ 条款、修订、评论、评审 API
  ├─ 公告 / 政策采集 API
  └─ 通知与飞书同步适配器

数据层
  ├─ 对象存储：原始文件、解析产物、导出物
  ├─ 关系数据库：标准、条款、审核、版本、权限
  ├─ 检索索引：标准段落、政策原文、引用关系
  └─ 审计日志：来源、哈希、操作人与时间
```

黑客松阶段可保留“前端状态 + 少量服务端适配器”；进入可试用版本后，优先补齐数据库与对象存储，再接入真实来源。

## 4. 模块一：标准协同编制与审核

### 4.1 模块目标

把一份受授权的标准 PDF / DOCX 转换为可编辑、可审核、可版本化的条款树，并让人工评审在条款级完成闭环。

### 4.2 输入、处理与输出

| 环节 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| 导入 | PDF / DOCX、来源 URL、标准编号 | 文件校验、哈希计算、存证 | `DocumentFile`、导入任务 |
| 解析 | 原始文件、解析器版本 | MinerU / Docling 版面与文本解析 | Markdown、JSON、表格、图片、解析日志 |
| 结构化 | 解析结果、人工校正 | 识别章节、条款、引用文件、术语、附录 | `Standard`、`Clause`、`Reference` |
| 审核 | 条款树、规则包、词表 | 规则匹配、证据定位、AI 候选建议 | `ReviewIssue` |
| 修订 | 目标条款、修改内容、理由 | 差异计算、权限校验、版本快照 | `Revision`、差异视图 |
| 评审 | 指定版本、评审组 | 评论、采纳/驳回、通知 | `Comment`、`NotificationEvent` |

### 4.3 条款对象最小模型

```text
Clause
  id                条款唯一标识
  standardId        所属标准
  parentId          父条款，形成树结构
  clauseNo          条款号，例如 6.2.1
  title             条款标题
  clauseType        scope / term / requirement / test / annex ...
  content           结构化或富文本内容
  sourceLocation    在原始文件中的页码、块号或坐标
  version           当前版本号
  status            draft / in_review / approved / archived
```

### 4.4 审核规则分层

| 规则层 | 示例 | 处理方式 |
| --- | --- | --- |
| 格式规则 | 编号跳号、标题层级错误、附录引用缺失 | 确定性规则，直接给出定位 |
| 规范性语言 | “应 / 宜 / 可”混用、强制性表述不清 | 词法规则 + 受控词表 |
| 可验证性 | 无测试条件、无单位、无判定阈值 | 字段完整性与模式匹配 |
| 一致性 | 术语多写法、引用标准版本冲突 | 跨条款索引与引用解析 |
| AI 辅助 | 长句改写、缺失条件候选、风险提示 | 返回候选与依据，人工确认 |

### 4.5 分步实施

1. **先固化条款 JSON**：用现有 `data/standard-data.js` 证明条款树展示，再定义稳定的 `Clause` 数据结构。
2. **接入解析任务**：将现有 MinerU 服务输出转换为标准化的解析任务记录，保留原文件和解析版本。
3. **实现三条硬规则**：优先完成“规范性用语”“单位/条件缺失”“引用文件”，每条必须有证据定位。
4. **实现修订留痕**：任何修改都形成前后内容、理由、作者、时间和状态，而不是覆盖原文本。
5. **接入评审闭环**：评论、问题状态和 SMTP 通知共用同一条版本记录。

### 4.6 验收口径

- 任意一份上传文件可保留来源、哈希和解析任务状态。
- 至少识别 3 类问题，并准确定位到条款与原文片段。
- 修订一个条款后，可查看修改前后内容、修改人、时间和理由。
- 不配置 SMTP / MinerU 时，系统显示明确的“未配置”提示，而不是伪造成功。

## 5. 模块二：公告、组织与标准追踪

### 5.1 模块目标

让用户在编辑一份标准时，看到相关标准状态、来源信息、起草组织和行业关联，而不是把编辑工作与外部变化割裂开。

### 5.2 输入、处理与输出

| 环节 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| 来源配置 | 站点、关键词、采集频率、授权说明 | 生成受控采集任务 | `SourceConfig` |
| 元数据采集 | 公开页面、授权 API 或人工录入 | 字段抽取、去重、状态比较 | `SourceRecord`、`Standard` 更新 |
| 关系维护 | 起草单位、技术委员会、企业、主题 | 人工维护或授权数据导入 | `Organization`、关系表 |
| 关联推荐 | 当前标准的关键词、ICS/CCS、引用关系 | 规则匹配或检索排序 | 关联标准 / 组织列表 |

### 5.3 实施策略

1. **先人工录入，后自动采集**：黑客松只维护 10～20 条高质量样例数据，保证演示可信。
2. **只采集合法元数据**：优先标准号、标题、状态、发布日期、实施日期、ICS/CCS、来源 URL；不假设可批量下载全文。
3. **为采集保留审计字段**：每个 `SourceRecord` 至少有 `sourceUrl`、`fetchedAt`、`rawHash`、`accessStatus`。
4. **接入采集器时分离运行**：Scrapy / Playwright 作为定时任务，不直接塞进页面或同步请求。

### 5.4 首批接口

| 接口 | 用途 | 当前阶段 |
| --- | --- | --- |
| `GET /api/standards/{id}` | 查询标准详情和条款树 | 需后端实现 |
| `GET /api/standards/{id}/related` | 查询关联公告、组织与标准 | 演示数据已在前端展示 |
| `POST /api/sources/{id}/collect` | 触发受控来源采集 | 后续接入 |
| `GET /api/sources/{id}/records` | 查看采集记录与变更 | 后续接入 |

## 6. 模块三：政策收集与解读

### 6.1 模块目标

把政策原文与标准制修订决策关联起来，帮助用户判断“为什么要改、改什么、影响谁”，但不让 AI 在没有依据的情况下发布结论。

### 6.2 输入、处理与输出

| 环节 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| 收集 | 政策来源、关键词、地区、产业 | 保存元数据、正文摘要与有效状态 | `Policy` |
| 分类 | 政策正文、标签体系 | 行业/地区/主题分类 | 分类标签 |
| 解读 | 原文段落、当前标准上下文 | AI 生成结构化草稿 | `InterpretationDraft` |
| 人审 | 草稿、原文证据 | 补证、修改、审核、发布 | 审核后的解读 |

### 6.3 AI 解读约束

- 输出固定为“适用对象、核心变化、建议动作、风险提示”。
- 每个结论至少引用一段 `PolicyEvidence`，可定位回原文 URL 或段落。
- 未审核状态只能标记为草稿，不能发送通知或作为正式建议。
- AI 无法从原文支持的结论必须以“不确定，需要人工确认”处理。

### 6.4 首批实施顺序

1. 保留现有高质量演示政策与原文链接。
2. 将政策对象与证据对象分开建模，先解决“结论可回链”。
3. 接入受控检索 / RAG 后再启用 AI 草稿生成。
4. 最后加入按角色推送和影响范围订阅。

## 7. 共用能力与接口边界

### 7.1 身份、权限与审计

最小角色为标准化工程师、政策研究人员、评审专家和管理员。每次导入、解析、修订、评审、通知和发布都需要记录：

```text
actorId + action + objectType + objectId + before/after + source + occurredAt
```

黑客松阶段可以使用固定演示角色；进入可试用版本时，先接入登录和基于角色的 API 权限校验。

### 7.2 文件与对象存储

- 原始文件、解析 Markdown、图片和 ZIP 放对象存储或受控磁盘目录。
- 数据库只保存元数据、哈希、存储键与权限信息。
- 解析产物以“原文件哈希 + 解析器版本”去重，避免重复解析。
- 用户上传文件与 MinerU 结果目录必须从 Git 排除。

### 7.3 通知与飞书集成

| 能力 | 当前实现 | 后续规范 |
| --- | --- | --- |
| 邮件评审通知 | 服务端 SMTP，固定收件人、冷却时间 | 通知事件入库、失败重试、模板版本化 |
| 飞书同步 | Markdown 追加到有权限的文档 | 保存目标文档 ID、同步事件与幂等键 |
| 站内通知 | 暂未实现 | 评审任务、@提及、状态变更统一通知中心 |

## 8. 实施顺序与交付物

| 阶段 | 目标 | 必须产出 | 完成判定 |
| --- | --- | --- | --- |
| A：演示闭环 | 让评委看懂主流程 | 工作台、演示数据、PDF 解析入口、部署站点 | 5 分钟走完“导入 → 审核 → 修订 → 评审 → 关联信息” |
| B：数据真实化 | 让一条流程持久化 | 数据库模型、对象存储、导入/条款/修订 API | 刷新页面后记录仍存在，原件可追溯 |
| C：审核可用化 | 让审核结果可信 | 规则包、术语库、证据定位、人工处置 | 至少 3 条规则可稳定复现并解释 |
| D：协同可用化 | 让多人共同工作 | 登录、角色、评论、版本、通知事件 | 两个角色可完成一次评审闭环 |
| E：生态接入 | 让外部变化进入系统 | 合规来源适配器、政策检索、关系模型 | 有审计记录的真实来源数据可更新 |

## 9. 测试与验收清单

### 功能测试

- [ ] 上传非 PDF、超过 30 MB、无 MinerU 凭据时有正确提示。
- [ ] 解析完成后能查看 Markdown、下载结果，并保留原始文件引用。
- [ ] 规则问题能跳转到目标条款，采纳/关闭后状态一致。
- [ ] 未配置 SMTP 时不发送；已配置时只能通知预设收件人。
- [ ] 飞书同步只追加、不覆盖，重复同步具有幂等保护。
- [ ] 政策解读每个结论可回链证据，未经审核不能推送。

### 安全与合规测试

- [ ] `.env*`、Token、SMTP 授权码和飞书密钥不进入 Git、浏览器源码或日志。
- [ ] 公开站点不能读取 `.git`、运行时目录或上传目录。
- [ ] 来源站点的访问规则和文件授权状态被记录。
- [ ] 公开接口限制文件类型、大小与频率，错误信息不泄露密钥。

## 10. 团队协作约定

- 先更新 PRD / 本文的对应模块，再开始跨模块实现，避免“页面已经做了、数据模型未定义”。
- 每项功能提交应说明：用户场景、输入、输出、权限、失败提示与验收方式。
- 不在前端写 Token，不上传 `.env.local`、原始标准全文或解析 ZIP。
- 演示数据必须显式标注为“演示”，真实来源数据必须保存来源和时间。
- 推送 `main` 会触发线上同步；合并前应执行 `npm run check`。

## 11. 下一轮最小任务建议

下一轮只选择一个可验证的小闭环，推荐顺序如下：

1. 将 PDF 解析结果映射成稳定的条款 JSON，并在工作台展示真实章节树。
2. 将“保存修订”从前端状态改为一条持久化 `Revision` 记录。
3. 增加三条可解释规则，并将问题写入 `ReviewIssue`。
4. 用一组受控样例数据替换公告、组织与政策的纯模拟内容。

完成任意一步后，更新 README 的“现阶段可交付内容”表和本文件的阶段状态，再进入下一步。
