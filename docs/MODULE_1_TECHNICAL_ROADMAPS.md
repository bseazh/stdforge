# 模块一：标准协同编制技术路线图

## 使用说明

本文件将模块一拆为 6 幅技术路线图。建议答辩时按图 1 到图 6 依次讲解：先讲总链路，再分别展开生成、协同、双语、审批和知识库。每幅图都包含输入、处理方案、核心数据和输出。

## 图 1：模块一端到端总路线

~~~mermaid
flowchart LR
    A[研发技术要求<br/>DOCX / PDF / TXT] --> B[文件解析与存证]
    T[参考标准 PDF<br/>企业模板 JSON] --> C[模板抽取与字段映射]
    B --> D[统一 Markdown<br/>原件哈希与来源]
    C --> E[章节结构与字段规则]
    D --> F[AI 草案编排]
    E --> F
    F --> G[标准草案]
    F --> H[编制说明]
    F --> I[预研报告]
    G --> J[条款协同审核]
    H --> J
    I --> J
    J --> K[飞书文档协同]
    K --> L[飞书审批与意见反馈]
    L --> M[已批准归档 / 发布]
    D --> N[知识库与索引]
    J --> N
    N --> O[Agent RAG<br/>检索、对比、审核建议]
    O --> J
~~~

| 维度 | 说明 |
| --- | --- |
| 主输入 | 研发技术要求、参考标准 PDF、企业模板和术语库。 |
| 主输出 | 三类草案、可编辑条款、飞书协作文档、审批结果和归档版本。 |
| 核心原则 | 原件保留、AI 只生成候选、人工确认后才能进入审批或发布。 |
| 当前代码 | 模块一页面、pdf-parser 服务、KDB 知识库、飞书同步与审批适配器。 |

## 图 2：AI 草案生成与模板映射路线

~~~mermaid
flowchart TB
    A[研发 DOCX / PDF / TXT] --> B{文件类型}
    B -->|PDF| C[MinerU 版面解析]
    B -->|DOCX / TXT| D[本地文本提取]
    C --> E[Markdown 中间层]
    D --> E
    F[参考标准 PDF] --> G[MinerU 模板解析]
    H[企业模板 JSON] --> I[章节、字段、必填规则]
    G --> J[模板 Markdown]
    J --> K[模板结构抽取]
    I --> K
    E --> L[字段识别与缺口检查]
    K --> M[字段到条款映射]
    L --> M
    M --> N[LLM 受控生成]
    N --> O[标准草案]
    N --> P[编制说明]
    N --> Q[预研报告]
    N --> R[来源字段与待确认项]
~~~

| 环节 | 实现方案 | 数据流 |
| --- | --- | --- |
| 文件解析 | PDF 使用 MinerU；DOCX/TXT 使用本地文本提取。 | 原件 -> Markdown、表格、图片、哈希。 |
| 模板抽取 | 参考标准 PDF 解析为章节结构；企业模板维护为 JSON。 | 模板 PDF/JSON -> section、field、rule。 |
| 映射 | 指标按对象、条件、限值、单位、判定方式拆分。 | source field -> target clause。 |
| 生成 | OpenAI 兼容 LLM；异常时使用确定性演示映射。 | 输入文本 + 模板 -> 三类草案。 |
| 保护 | 未确认数值、引用和法规不得被模型补造。 | 缺口 -> 待确认项。 |

## 图 3：条款协同与规范性审核路线

~~~mermaid
flowchart LR
    A[草案 Markdown] --> B[章节和条款结构化]
    B --> C[Clause 树]
    C --> D[确定性规则]
    C --> E[术语与引用一致性]
    C --> F[LLM 审核建议]
    D --> G[审核问题队列]
    E --> G
    F --> G
    G --> H[标准化工程师修订]
    H --> I[Revision 版本快照]
    I --> J[飞书文档追加同步]
    J --> K[多人编辑 / 评论 / @提醒]
    K --> L[确认回写平台新版本]
    L --> C
~~~

| 审核层 | 处理方式 | 关键数据 |
| --- | --- | --- |
| 格式和完整性 | 条款编号、标题层级、单位、附录引用等确定性规则。 | clauseId、ruleId、evidence、severity。 |
| 规范性语言 | 受控词表检查应、宜、可等规范用语。 | term、location、suggestion。 |
| 可验证性 | 检查是否存在条件、限值、单位、方法和判定规则。 | requirement、testMethod、decision。 |
| LLM 候选 | 对长句、条件缺失和引用风险给出候选修改。 | modelVersion、candidate、sourceEvidence。 |
| 版本留痕 | 每次人工确认保存前后内容、理由、人员和时间。 | before、after、author、createdAt。 |

## 图 4：中英文版本协同输出路线

~~~mermaid
flowchart TB
    A[已确认中文草案] --> B[按标题和自然段切分]
    B --> C[中文 Segment 列表]
    D[行业术语库<br/>中英术语对照] --> E[术语约束]
    C --> F[LLM 段落翻译]
    E --> F
    F --> G[英文 Segment 列表]
    C --> H[中英一一对齐]
    G --> H
    H --> I[术语和数值校验]
    I --> J[中英对照稿]
    I --> K[纯英文稿]
    J --> L[中文 / 英文版本快照]
    K --> L
    L --> M[导出 Markdown / DOCX / PDF]
~~~

| 环节 | 方案 | 约束 |
| --- | --- | --- |
| 切分 | 按标题和自然段生成稳定 segmentId。 | 不跨条款合并，保持编号顺序。 |
| 翻译 | LLM 返回与中文相同的 segmentId。 | 不改变条款号、数值、单位、公式和引用编号。 |
| 术语 | GlossaryTerm 维护领域词、译法、备注和版本。 | 同一术语优先使用术语库译法。 |
| 修订 | 分别保存中文、英文版本和修订原因。 | 英文人工修改不覆盖机器初稿。 |
| 现有复用 | module3/source/server/bilingual-translation.mjs。 | 接入模块一前需主服务化和持久化。 |

## 图 5：飞书协同、审批、意见反馈与发布路线

~~~mermaid
flowchart LR
    A[平台草案版本] --> B[同步飞书文档]
    B --> C[飞书在线编辑]
    C --> D[飞书评论 / @协作人]
    D --> E[意见归集]
    E --> F[平台条款修改]
    F --> G[创建飞书审批实例]
    G --> H[预审]
    H --> I[专家评审]
    I --> J[复核]
    J --> K[发布确认]
    K -->|通过| L[审批结果回写]
    L --> M[归档版本 + 发布公告]
    K -->|退回| E
~~~

| 节点 | 飞书能力 | 平台职责 |
| --- | --- | --- |
| 在线协同 | 文档编辑、评论、@提醒。 | 记录草案版本、同步事件和文档链接。 |
| 预审和专家评审 | 审批表单、待办和审批人。 | 传入标准名称、文档链接、审查说明和版本。 |
| 意见反馈 | 评论和外部意见附件。 | 归集为 ReviewComment，生成意见汇总处理表。 |
| 状态回写 | APPROVED、REJECTED、CANCELED。 | 更新 Draft 状态，冻结批准版本。 |
| 发布 | 审批完成后生成公告或调用企业 OA。 | 保留版本哈希、审批实例和归档链接。 |

## 图 6：标准知识库与 Agent RAG 路线

~~~mermaid
flowchart TB
    A[标准 PDF / DOCX<br/>技术资料 / 历史版本] --> B[解析与文本标准化]
    B --> C[文件哈希与版本判断]
    C --> D[分块索引]
    D --> E[关键词 / 术语 / 引用索引]
    D --> F[向量索引<br/>后续增强]
    E --> G[任务规划 Agent]
    F --> G
    G --> H[standard-search]
    G --> I[standard-diff]
    G --> J[template-extract]
    G --> K[term-check]
    G --> L[citation-check]
    H --> M[带证据的结果]
    I --> M
    J --> M
    K --> M
    L --> M
    M --> N[审核建议 / 差异报告 / 模板候选]
~~~

| 层 | 当前能力 | 目标增强 |
| --- | --- | --- |
| 文本层 | MinerU、DOCX/TXT 提取、Markdown 持久化。 | 表格、公式、图片和条款位置结构化。 |
| 索引层 | 哈希去重、约 900 字符分块、中文双字词和英文 token 检索。 | 向量索引、引用关系图和版本差异索引。 |
| 回答层 | LLM 基于命中片段归纳并返回引用。 | Agent 选择检索、对比、术语和引用核验技能。 |
| 更新层 | 文件哈希变化后重新入库。 | 模板、术语库、解析器版本变化触发增量索引。 |
| 安全层 | 原文片段和引用可追溯。 | 任务权限、敏感文档隔离、审计日志。 |

## 图与模块的答辩顺序

1. 图 1：先解释模块一为何不是单点 AI 写作，而是一条受控编制链路。
2. 图 2：展示最核心的输入、模板、LLM 和三类输出。
3. 图 3：说明生成后仍需条款审核和人工修订。
4. 图 4：说明中英文不是机器直译，而是术语库和版本协同。
5. 图 5：说明企业内协作、审批和发布复用飞书现成能力。
6. 图 6：说明知识库不是只做 embedding，而是通过受控技能完成搜索、对比和核验。
